# AGENTIC Knowledge Architecture
## Platform-Level and Project-Level Knowledge

**Version:** 1.0  
**Status:** Approved Design

## 1. Purpose

The AGENTIC Knowledge Architecture separates reusable engineering knowledge from project-specific knowledge.

- **Platform-Level Knowledge** is reusable across projects.
- **Project-Level Knowledge** is specific to one project.

This separation allows AGENTIC to reuse engineering expertise while keeping project-specific truth and context isolated.

## 2. Core Principle

> **Platform Knowledge provides reusable engineering guidance. Project Knowledge provides project-specific truth. The Agent synthesizes both. The User remains the authority for approval.**

Generic best practice must not silently replace a project-specific requirement.

## 3. Architecture

```text
                    AGENTIC PLATFORM
                          │
              ┌───────────┴───────────┐
              │                       │
      PLATFORM KNOWLEDGE       PROJECT KNOWLEDGE
       Reusable across          Specific to one
          projects                 project
              │                       │
              └───────────┬───────────┘
                          ↓
                    AGENT CONTEXT
                          ↓
                 Engineering Lifecycle
```

## 4. Platform-Level Knowledge

Platform Knowledge provides reusable engineering knowledge that AGENTIC can apply across projects.

Examples:

- Business Process patterns
- Activity patterns
- Industry best practices
- Engineering patterns
- Standards and frameworks
- Reference architectures
- UI/UX patterns
- Data modeling patterns
- Non-functional requirement patterns
- Technology patterns
- Generalized lessons learned
- Reusable templates and examples

For Business Process and Activity generation, examples include:

```text
Request → Review → Approve → Fulfill
Submit → Validate → Correct → Approve
Register → Verify → Activate
Plan → Execute → Monitor → Close
Incident → Diagnose → Resolve → Verify
```

These are references for generating proposals, not mandatory project requirements.

## 5. Project-Level Knowledge

Project Knowledge provides factual, contextual, and authoritative knowledge specific to the current project.

Examples:

- Business requirements
- Applicable regulations
- Policies
- Standard Operating Procedures
- Existing business processes
- Existing systems
- Existing data models
- Existing architecture
- Stakeholder information
- Project decisions
- Project-specific terminology
- Current-state processes
- Approved engineering artifacts
- Other project reference documents

## 6. Comparison

| Dimension | Platform Knowledge | Project Knowledge |
|---|---|---|
| Scope | All projects | One project |
| Purpose | Reusable engineering guidance | Project-specific truth and context |
| Reusability | High | Normally project-specific |
| Examples | Patterns, standards, best practices | SOPs, regulations, requirements |
| Authority | Reference | Project authority |
| Lifecycle usage | Across projects | Within the project |
| Guides Agent proposals | Yes | Yes |
| Overrides project requirements | No | Yes |

## 7. Knowledge Precedence

When Platform Knowledge and Project Knowledge differ, authoritative Project Knowledge takes precedence.

```text
Platform Knowledge
       +
Project Knowledge
       ↓
   Conflict?
   /        No         Yes
 ↓           ↓
Use both   Evaluate authority
             ↓
      Project requirement
          takes precedence
             ↓
          User review
```

Example:

```text
Platform Knowledge:
Two-step approval is recommended.

Project Regulation:
Three approval levels are mandatory.

Agent:
→ Propose three approval levels.
→ Do not replace the project requirement with the platform pattern.
```

## 8. Types of Knowledge

The Agent should distinguish:

### Requirement
A mandatory condition established by an authoritative project source.

### Existing Practice
How the organization currently performs the work.

### Best Practice
A recommended practice from Platform Knowledge or another accepted reference.

### Agent Inference
A recommendation generated by the Agent from available knowledge and reasoning.

The Agent must not silently convert a best practice or inference into a mandatory project requirement.

## 9. Conflict Handling

When Platform Knowledge and Project Knowledge appear to conflict, the Agent should identify and explain the conflict.

Example:

```text
Platform Knowledge:
Independent review is recommended before approval.

Project SOP:
The current process does not include independent review.

Agent:
The project SOP does not currently include independent review.
Platform process guidance recommends it for this type of process.

Recommendation:
Consider adding independent review as a proposed control.

User:
Accept / Reject / Modify
```

The User remains the decision authority.

## 10. Agent Usage

The Agent uses both knowledge levels when generating engineering outputs.

```text
Project Context
      +
Project Knowledge
      +
Platform Knowledge
      +
Applicable Glossary
      ↓
Knowledge Retrieval
      ↓
Agent Reasoning
      ↓
Proposed Engineering Output
      ↓
User Review / Revision
      ↓
User Approval
```

Only knowledge relevant to the current lifecycle stage and engineering task should be retrieved.

## 11. Relationship with Glossary

Knowledge Architecture works with the approved AGENTIC Glossary structure:

```text
COMMON GLOSSARY
       ↓
PROJECT GLOSSARY
       ↓
PLATFORM KNOWLEDGE + PROJECT KNOWLEDGE
       ↓
AGENT CONTEXT
       ↓
ENGINEERING LIFECYCLE
```

### Common Glossary

Provides authoritative meanings reusable across projects.

### Project Glossary

Provides project-specific terminology and contextual definitions.

The Agent should identify conflicts between common and project terminology rather than silently redefining authoritative terms.

## 14. Governance Boundary

### Platform Knowledge must not:

- Contain confidential project-specific information.
- Assume a particular project's business rules.
- Override project requirements.
- Become a hidden source of mandatory project behavior.

### Project Knowledge must not:

- Automatically become reusable Platform Knowledge.
- Modify platform-wide knowledge without governance.
- Be assumed to apply to other projects.

## 15. Knowledge Promotion

A useful project-specific insight may be generalized and promoted to Platform Knowledge through explicit governance:

```text
Project Knowledge
       ↓
Identify reusable insight
       ↓
Generalize
       ↓
Review
       ↓
Approve
       ↓
Platform Knowledge
```

Only the reusable principle or pattern should be promoted, not project-specific information.

## 16. Design Principles

1. **Platform Knowledge guides.**
2. **Project Knowledge governs.**
3. **The Agent synthesizes and proposes.**
4. **The User approves.**

This enables AGENTIC to combine reusable engineering intelligence with project-specific truth while keeping projects isolated and the engineering lifecycle simple.
