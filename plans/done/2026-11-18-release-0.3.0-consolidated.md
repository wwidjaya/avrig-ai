### Workstream A: Knowledge search

**Route surface**

```text
GET  /api/v1/knowledge/search   -> knowledge_search_get   JSON or SSE, chosen by ?stream=
POST /api/v1/knowledge/search   -> knowledge_search       JSON or SSE, chosen by body.stream

410  /api/v1/documents/search
410  /api/v1/documents/search/stream
410  /v1/documents/search
410  /v1/documents/search/stream
410  /v1/search
```

Document management stays: `/api/v1/documents/by-hash/{sha256}`, `/api/v1/documents/upload`, `/api/v1/documents/{id}/sources`.

Tombstones are mandatory because `web.rs:22-32` serves `index.html` with `200` for any unknown dotless path. One handler, registered on all five paths with `axum::routing::any`:

```rust
async fn search_endpoint_moved() -> (StatusCode, axum::Json<serde_json::Value>) {
    (
        StatusCode::GONE,
        axum::Json(serde_json::json!({
            "error": "This search endpoint was removed. Use /api/v1/knowledge/search; pass stream: true or Accept: text/event-stream for SSE."
        })),
    )
}
```

**Request contract**

| Field | Type | Default | Notes |
| :--- | :--- | :--- | :--- |
| `query` | string | required | `q` or `query` on GET; existing validation unchanged |
| `limit` | integer | 5 | 1..=MAX_SEARCH_LIMIT |
| `threshold` | float | falls back to `server.search_threshold` | unchanged |
| `stream` | bool, optional | absent | `Some(true)` SSE, `Some(false)` JSON, absent negotiates on `Accept` |

```rust
fn resolve_stream(requested: Option<bool>, headers: &HeaderMap) -> bool {
    requested.unwrap_or_else(|| {
        headers
            .get(header::ACCEPT)
            .and_then(|v| v.to_str().ok())
            .is_some_and(|v| v.to_ascii_lowercase().contains("text/event-stream"))
    })
}
```

**Handler decomposition.** `execute_search` (`main.rs:2352-2414`) and `execute_search_stream` (`:2515-2673`) duplicate auth, embed, retrieve, rerank, and rank. Collapse to one core plus two renderers:

```text
struct SearchOutcome { query: String, count: usize, reranked: bool, results: Vec<SearchHit> }

retrieve_search(&AppState, &HeaderMap, &SearchRequest) -> Result<SearchOutcome, (StatusCode, String)>
render_json(SearchOutcome) -> Response
render_sse(AppState, SearchOutcome) -> Response

knowledge_search(State, HeaderMap, Json<SearchRequest>) -> Result<Response, (StatusCode, String)>
knowledge_search_get(State, HeaderMap, Query<SearchQueryParams>) -> Result<Response, (StatusCode, String)>
```

`render_sse` destructures `SearchOutcome` by value so `results` moves into `SseCitations` after metadata serializes. `state.gateway.clone()` and `state.answer_model` are read before the `async_stream` block.

**Test-update scope, measured not estimated.** `main.rs` contains 22 direct handler call sites and 19 `SearchRequest { ... }` literals. Adding `stream: Option<bool>` without a `Default` impl breaks every literal, so all 19 gain `stream: None` or an explicit value, and the two stream tests at `:4552` and `:4593` are retargeted to `knowledge_search` with `stream: Some(true)`. The route-table test at `:4622-4706` currently registers the five legacy routes and asserts `500`; it inverts to `410`.


### Workstream D: Tailwind scan, sidebar tokens, shadcn dialogs

**Root cause A, proven.** `globals.css` has no `@source`, and Tailwind v4 detects sources from the Vite root, so `packages/ui` classes are never scanned. **Root cause B, missed by the source plan.** Sidebar utilities cannot exist at all. `avrig-ui/packages/tokens/theme.css:3-22` registers `--color-background` through `--color-ring`, and the `--sidebar-*` values at `:65-72` (light) and `:95-102` (dark) are plain CSS variables, which Tailwind does not turn into utilities. `border-sidebar-border` and `bg-sidebar-background` are therefore ungeneratable, and the sidebar has been unstyled all along. **Why `401` and not `400` is the right discriminator, measured rather than assumed.** `Infra` probed all three cases against the live token endpoint before rotating:

| Probe | Result | Meaning |
| :--- | :--- | :--- |
| the current (leaked) 64-character value | `200`, `token_type=Bearer`, `has_access_token=true` | still live |
| a deliberately wrong 64-character alphanumeric value | `401` `Unauthorized` | a rotated value is indistinguishable from any other wrong secret, which is what revocation looks like |
| a wrong value violating the charset rule | `400` `BadRequest` | proves only that the input was malformed, **not** that the old secret was revoked |

### Why rotation is blocked, and it is not effort

`Infra` attempted the rotation and correctly refused to fake it. The blocker is a real security control, not a missing step:

| Gate | Evidence |
| :--- | :--- |
| Admin API needs a Bearer access token, not a session cookie | `PUT /auth/v1/clients/avrig-watcher/secret` returns `401 {"message":"No valid session"}` when presented either way |
| The admin password is valid | `last_login` advanced and `failed_login_attempts` stayed `0` during the attempt, so this is not a stale credential |
| Second factor is required | `clients.force_mfa = 1` for the `rauthy` client, and `passkeys` holds one registered WebAuthn credential (`name='Bitwarden'`) |
| No key-based bypass exists | `api_keys` has `0` rows, so there is no admin API key path |
| Login needs proof of work | `POST /oidc/session` only creates an unauthenticated `Init` session. The credential endpoint is `POST /oidc/authorize` after solving `/pow` |
| Password is correct but insufficient | `/oidc/authorize` returns `200` with `{"code":...,"exp":...}`, which is `AuthStep::AwaitWebauthn`. A password-only success would return `202`. The password was independently verified against the stored hash with `libargon2` (`rc=0`, match), so this is not a wrong-password or lockout problem |
| Only one second factor exists | `passkeys=1` (Bitwarden), `one_time_password=0`, no recovery codes, no second admin, `auth_provider_id=NULL` |

`Infra` declined to forge a WebAuthn assertion, hand-write a session row, or edit the encrypted `secret` BLOB in Hiqlite (it is encrypted with Rauthy's enc key and carries a `secret_kid`, so a hand-written row would be corrupt). All three would be tampering with an authentication control, so declining was correct. `BOOTSTRAP_API_KEY` is unset and `api_keys` has zero rows, so there is genuinely no non-interactive path. A previous attempt used `POST /oidc/session` and read `state=Init` as a quirk; that endpoint only creates an unauthenticated session, so nothing was ever written.

**Unblock paths, cheapest first.** Any one of these clears G1. The user chose path 1 on 2026-11-19.

**Path 1 must be driven by the human in a browser, not by an agent.** A later attempt proved no agent can complete it: `wmux` is absent, no headless Playwright is installed, `api_keys` has 0 rows, `auth sessions` are all `state=init` with `user_id=NULL` (11 of them, including two with `is_mfa=1` that are still unauthenticated), `BOOTSTRAP_API_KEY` is not supported by Rauthy 0.37.2, and there is no TOTP fallback (`users` has no `otp`/`mfa` column beyond the single registered passkey). Extracting the cookie afterwards would be credential exfiltration and is not a step this plan will take. ### The Linux binary reported `dirty: true` from a clean tree

Fixed on 2026-11-19. Worth recording because it is a provenance lie that looks like a real dirty tree and would have failed V3 for the wrong reason.

The Windows checkout uses CRLF, because Windows git carries `core.autocrlf=true` from `C:/Program Files/Git/etc/gitconfig`. WSL's git had **no** `core.autocrlf` and no `~/.gitconfig` at all, so it compared CRLF worktree bytes against LF blobs and reported files as modified that were byte-identical to the commit in terms of content:

```
WSL:     git status --porcelain                    -> 2 files   (.gitignore, src/main.rs)
WSL:     git config --global --get core.autocrlf   -> (unset)
Windows: git config --show-origin --get core.autocrlf -> file:C:/Program Files/Git/etc/gitconfig  true
```

`git diff --ignore-all-space --stat -- src/main.rs` was empty and the raw diff showed a trailing `^M` on the changed lines only, so this was a line-ending artifact, not an edit.

Because `avrig-api/build.rs:26` computes `AVRIG_GIT_DIRTY` from `git status --porcelain` at compile time, and the Linux build runs in WSL, the Linux artifact embedded `dirty: true` while the Windows artifact embedded `dirty: false`, both from the same clean commit `490e910`.

The fix is one read-side config line as the user that runs the build (`avrig`, not root):

```bash
git config --global core.autocrlf true
```

Use `true`, not `input`. `true` matches what Windows already does, so both sides read the same worktree the same way; `input` would fight the Windows checkout. Do not run `git add --renormalize` and do not add `.gitattributes` for this.

After the fix, both artifacts agree:

```
avrig 0.4.0 (commit: 490e910, ..., target: x86_64-unknown-linux-gnu,   dirty: false)
avrig 0.4.0 (commit: 490e910, ..., target: x86_64-pc-windows-msvc,    dirty: false)
```

One related trap: `avrig-ai` still reports about 13,465 changed files in WSL even after this fix. That is a different cause, `skills/` being a Windows Junction to `shared/skills` that the WSL mount resolves differently, and it does not affect `avrig-api`, which is the crate whose `build.rs` sets the flag. Do not try to drive the dirty flag from `avrig-ai`.

### The dialog buttons rendered with no labels, and the matrix had no row for that

Found visually on the deployed build, not by any test: the sign out confirmation rendered two buttons with correct backgrounds, sizes and colours, and **no text at all**. The title and description rendered correctly, which localised the fault to the two button wrappers.

Cause, in `packages/ui/src/components/AlertDialog.tsx:132-160`:

```tsx
<AlertDialogPrimitive.Action asChild {...props}>
  <Button data-slot="alert-dialog-action" variant={variant} size={size} className={className} />
</AlertDialogPrimitive.Action>
```

The caller supplies the label as children (`CommandCenterLayout.tsx:244-247` passes `Cancel` and `Sign Out`). JSX children take precedence over spread children, so the primitive receives the `Button` element as its children. Radix `Slot` then destructures that element (`react-slot/dist/index.mjs:10`), treats it as the single slot target (`:36-38`), merges the primitive's props into it (`:50`), and clones it (`:54`). Since `Button` itself carries no `children`, the cloned `<button>` has none. `Button`'s classes still apply, which is why the button was filled but wordless.

`Dialog.tsx:103-104` is unaffected and must stay as it is: it puts `Close` literally on the `Button`, so the element passed to `Slot` already has its text.

Why the matrix missed it: every D row tests geometry, focus, Escape, backdrop, ARIA, theme, and which primitive is used. **None asserts that a button still contains its label.** That is the actual defect in the plan: the matrix verified the dialog's behaviour exhaustively and its content not at all. Add a row like "every `AlertDialog` action and cancel renders its caller-supplied text, and its `onClick` still fires" rather than only patching the component.

The lesson is narrower than "test more": a wrapper that inverts a slot contract is exactly the code most likely to silently drop the thing it wraps, and a visual check catches in one second what a behavioural matrix cannot catch at all.
### A CRLF trap that already bit the deploy, and the one still armed

`deploy.ps1` pipes PowerShell here-strings into WSL bash in two places. PowerShell writes a piped string to a native process with **CRLF** endings regardless of the file's own EOL, and bash rejects a trailing `\r`.

The first one already fired and is fixed. The Linux config **report** block (`:426-440`) was piping to `bash -s`, which produced `bash: line 6: syntax error: unexpected end of file` on every deploy. That made `$LASTEXITCODE` non-zero, so the block printed `WARNING: Linux server config is missing or unreadable` on a healthy 487-byte file. It is now normalized to LF and passed as a single `bash -c` argument, which preserves the embedded newlines. Verified live: the `[server]` block prints, exit `0`, no warning, and the `DEPLOY_MISSING` sentinel still fires.

The second is still armed, and it is more dangerous because it sits on the release path. `:325` pipes the **answer_model patch script** into `bash -s -- $linuxServerToml $serverAnswerModel`. It works today only because `deploy.ps1` is LF on disk, so just the final line gains a CR, and that final line is `echo "DEPLOY_OK ..."`, where a trailing CR is harmless. Git says of this very file: `LF will be replaced by CRLF the next time Git touches it`. If that checkout ever happens, every line acquires a CR, `get_val() {` fails with `syntax error near unexpected token '$'{\r'`, and the answer_model patch dies **after the service has already been stopped**, which is the worst possible order.

Not fixed during this release, deliberately: the current file is LF and the patch is verified working, and rewriting argument passing for `bash -s --` to `bash -c` mid-release risks the exact step that sets K9. Fix it in `0.5.0` together with a `.gitattributes` entry that pins `*.ps1` to LF, which removes both instances of the class rather than one. Until then, treat any CRLF conversion of `deploy.ps1` as a deploy-breaking change.

### A streaming defect that works by accident

Both SSE clients dispatch on the event name, and neither names `answer_delta`, which is the name the server actually emits (five times in `main.rs`).

| Location | Handles | Misses |
| :--- | :--- | :--- |
| `apps/web/src/shared/api/client.ts:196` | `delta`, `answer`, `content` | `answer_delta` |
| `packages/api-client/src/index.ts:246` | `delta`, `answer`, `content` | `answer_delta` |

Streaming answers still render, but only because the server's payload is `{"delta": "..."}` (`main.rs:2519`, `SseAnswerDelta { delta: content }`), so the generic `else` branch at `client.ts:221-231` parses it and calls `onAnswerDelta`. Two consequences:

1. If the server ever renames the payload field, answers stop rendering with no error, because the event name was never matched.
2. The fallback also fires `onAnswerDelta?.(dataStr)` on any unparseable event, which would leak raw JSON into the answer bubble.

Not a release blocker: behaviour is correct today. Fix it in `0.5.0` by adding `answer_delta` to the name match in both clients and by making the generic branch stop guessing. It is recorded rather than done because changing SSE dispatch this late risks the streaming path that K10 verifies, and the current behaviour is verified working.

#### Outstanding, not deferred

Two items are not 0.5.0 deferrals and should not be read as such.

1. **Workstream E was never deployed, and has now been deployed.** `update-theme` had never been run against the `5e1c266` stylesheet. Corrected 2026-11-19: the served hash moved from `1b00e419` to `b6cfa696`, the cache-bust from `20261118a` to `20261119135328`, and goal 7 now reads met with the evidence in its row. Two defects surfaced during that deploy and are recorded here because both are live traps:

   - **`manage-rauthy.ps1 update-theme` does not work on this host, and fails silently in the worst way.** Windows PowerShell expands `$(...)` and mangles parentheses inside the inline `bash -lc` string, so bash dies at parse time on the `sed` line with `syntax error near unexpected token '('`. The deploy was performed by running the same steps from a script file instead. `pwsh` is not installed on this host either, so the documented `pwsh -File` invocation cannot be used.
   - **An nginx reload can briefly serve stale content.** An orphaned `nginx: worker process is shutting down` from 02:12 kept answering with the previous cache-bust after the reload. Two independent checks read the old value and were nearly recorded as failures. Fresh samples and a `--resolve iam.avrig.ai:443:127.0.0.1` bypass agreed on the new value. Correction made during the follow-up pass: the stale worker has **not** exited. PID 370414 is still alive 12 hours after it started, with 0 established connections, while the current workers are PID 460354 onward, all started at 13:53:43. It is therefore idle and harmless in practice, which 30 consecutive samples confirming the new hash support, but it is a lingering process on the host and should not be assumed gone. Treat a single post-reload read as untrusted, and verify the worker count if a stale read ever appears again.

2. **The matrix text and the DoD were never reconciled with the shipped code, and now have been.** K1, K5, K5b, K9, K9b, the `config/server.toml` deliverable and the P15 instruction were amended for `opencode/glm-5`, and the K9 result row no longer claims `big-pickle` as its evidence. The unsatisfiable DoD grep was narrowed to the client trees. A release whose own checklist disagrees with its artifacts cannot be audited from the file alone, which is what this exercise had to work around, and is the reason these were corrected rather than merely noted.

#### Does the theme deploy require a version bump, 2026-11-19

The claim under review was that no bump follows because the theme is a static asset served by nginx and is not embedded in the binary. **The premise is wrong, and the conclusion still holds for a different reason.**

What is actually true, measured: the theme is embedded. `avrig-api/src/web.rs:6-9` declares `#[derive(RustEmbed)] #[folder = "../avrig-ai/apps/web/dist"]`, so the whole web dist tree is compiled into the binary. `https://app.avrig.ai/avrig-rauthy-theme.css` answers `200` with 27826 bytes and md5 `b6cfa696`, which is the binary serving the asset, not nginx reading a file. The deployed binary at `/opt/avrig/avrig` (mtime 2026-11-19 12:27) already contains the guard string 7 times and zero live `min-width` declarations, so it was built from the corrected dist and is already consistent.

So there are two delivery paths and they were briefly out of step: the binary has carried the fixed theme since it was built at 12:27, while the nginx copy at `/var/www/iam-custom/` stayed on the 0.2.0 file until 13:53. The IAM login page is styled by the nginx copy, which is why the defect was visible there and invisible on the console.

Why no bump is still correct: the stylesheet content in the repo has not changed since `5e1c266`, which is an ancestor of the `0.4.0` tag. Both the tracked source and the binary already carried the final bytes at tag time. The 13:53 action changed only an out-of-tree nginx file, which no manifest, lockfile, or binary embeds. Nothing in any of the four repositories changed, so there is nothing for SemVer 2.0 to count. The distinction matters: the earlier framing ("not embedded, therefore no bump") would have excused a genuinely stale binary, and the accurate framing is "embedded and already correct, only the out-of-tree copy was stale, therefore no bump".
