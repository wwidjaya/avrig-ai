## Key Detailed Design

### Workstream A: Knowledge search

**Route surface**

```text
GET  /api/v1/knowledge/search   -> knowledge_search_get   JSON or SSE, chosen by ?stream=
POST /api/v1/knowledge/search   -> knowledge_search       JSON or SSE, chosen by body.stream

410  /api/v1/documents/search
410  /api/v1/documents/search/stream
410  /v1/documents/search
410  /v1/documents/search/stream
410  /v1/search
```

Document management stays: `/api/v1/documents/by-hash/{sha256}`, `/api/v1/documents/upload`, `/api/v1/documents/{id}/sources`.

Tombstones are mandatory because `web.rs:22-32` serves `index.html` with `200` for any unknown dotless path. One handler, registered on all five paths with `axum::routing::any`:

```rust
async fn search_endpoint_moved() -> (StatusCode, axum::Json<serde_json::Value>) {
    (
        StatusCode::GONE,
        axum::Json(serde_json::json!({
            "error": "This search endpoint was removed. Use /api/v1/knowledge/search; pass stream: true or Accept: text/event-stream for SSE."
        })),
    )
}
```

**Request contract**

| Field | Type | Default | Notes |
| :--- | :--- | :--- | :--- |
| `query` | string | required | `q` or `query` on GET; existing validation unchanged |
| `limit` | integer | 5 | 1..=MAX_SEARCH_LIMIT |
| `threshold` | float | falls back to `server.search_threshold` | unchanged |
| `stream` | bool, optional | absent | `Some(true)` SSE, `Some(false)` JSON, absent negotiates on `Accept` |

```rust
fn resolve_stream(requested: Option<bool>, headers: &HeaderMap) -> bool {
    requested.unwrap_or_else(|| {
        headers
            .get(header::ACCEPT)
            .and_then(|v| v.to_str().ok())
            .is_some_and(|v| v.to_ascii_lowercase().contains("text/event-stream"))
    })
}
```

**Handler decomposition.** `execute_search` (`main.rs:2352-2414`) and `execute_search_stream` (`:2515-2673`) duplicate auth, embed, retrieve, rerank, and rank. Collapse to one core plus two renderers:

```text
struct SearchOutcome { query: String, count: usize, reranked: bool, results: Vec<SearchHit> }

retrieve_search(&AppState, &HeaderMap, &SearchRequest) -> Result<SearchOutcome, (StatusCode, String)>
render_json(SearchOutcome) -> Response
render_sse(AppState, SearchOutcome) -> Response

knowledge_search(State, HeaderMap, Json<SearchRequest>) -> Result<Response, (StatusCode, String)>
knowledge_search_get(State, HeaderMap, Query<SearchQueryParams>) -> Result<Response, (StatusCode, String)>
```

`render_sse` destructures `SearchOutcome` by value so `results` moves into `SseCitations` after metadata serializes. `state.gateway.clone()` and `state.answer_model` are read before the `async_stream` block.

**Test-update scope, measured not estimated.** `main.rs` contains 22 direct handler call sites and 19 `SearchRequest { ... }` literals. Adding `stream: Option<bool>` without a `Default` impl breaks every literal, so all 19 gain `stream: None` or an explicit value, and the two stream tests at `:4552` and `:4593` are retargeted to `knowledge_search` with `stream: Some(true)`. The route-table test at `:4622-4706` currently registers the five legacy routes and asserts `500`; it inverts to `410`.

**Answer model resolution**

```text

provider prefix     opencode  (registered direct provider, case-insensitive)
base model          big-pickle (forwarded upstream unchanged)
upstream            POST https://opencode.ai/inference/openai/v1/chat/completions
```

### Why rotation is blocked, and it is not effort

`Infra` attempted the rotation and correctly refused to fake it. The blocker is a real security control, not a missing step:

| Gate | Evidence |
| :--- | :--- |
| Admin API needs a Bearer access token, not a session cookie | `PUT /auth/v1/clients/avrig-watcher/secret` returns `401 {"message":"No valid session"}` when presented either way |
| The admin password is valid | `last_login` advanced and `failed_login_attempts` stayed `0` during the attempt, so this is not a stale credential |
| Second factor is required | `clients.force_mfa = 1` for the `rauthy` client, and `passkeys` holds one registered WebAuthn credential (`name='Bitwarden'`) |
| No key-based bypass exists | `api_keys` has `0` rows, so there is no admin API key path |
| Login needs proof of work | `POST /oidc/session` only creates an unauthenticated `Init` session. The credential endpoint is `POST /oidc/authorize` after solving `/pow` |
| Password is correct but insufficient | `/oidc/authorize` returns `200` with `{"code":...,"exp":...}`, which is `AuthStep::AwaitWebauthn`. A password-only success would return `202`. The password was independently verified against the stored hash with `libargon2` (`rc=0`, match), so this is not a wrong-password or lockout problem |
| Only one second factor exists | `passkeys=1` (Bitwarden), `one_time_password=0`, no recovery codes, no second admin, `auth_provider_id=NULL` |

`Infra` declined to forge a WebAuthn assertion, hand-write a session row, or edit the encrypted `secret` BLOB in Hiqlite (it is encrypted with Rauthy's enc key and carries a `secret_kid`, so a hand-written row would be corrupt). All three would be tampering with an authentication control, so declining was correct. `BOOTSTRAP_API_KEY` is unset and `api_keys` has zero rows, so there is genuinely no non-interactive path. A previous attempt used `POST /oidc/session` and read `state=Init` as a quirk; that endpoint only creates an unauthenticated session, so nothing was ever written.

**Unblock paths, cheapest first.** Any one of these clears G1. The user chose path 1 on 2026-11-19.

**Path 1 must be driven by the human in a browser, not by an agent.** A later attempt proved no agent can complete it: `wmux` is absent, no headless Playwright is installed, `api_keys` has 0 rows, `auth sessions` are all `state=init` with `user_id=NULL` (11 of them, including two with `is_mfa=1` that are still unauthenticated), `BOOTSTRAP_API_KEY` is not supported by Rauthy 0.37.2, and there is no TOTP fallback (`users` has no `otp`/`mfa` column beyond the single registered passkey). A WebAuthn assertion must be signed by the key inside the human's authenticator, bound to `https://iam.avrig.ai`; a scripted session cannot produce it, and even an approval typed into a browser would land in that browser's session, not the agent's. Extracting the cookie afterwards would be credential exfiltration and is not a step this plan will take. So the rotation is a human action, and the agent's job is only the file patch, the restarts and the proofs.

The exact steps, so nothing is ambiguous:

1. Open `https://iam.avrig.ai/auth/v1/admin` and authenticate with the registered passkey. That satisfies `force_mfa` and mints an admin session.
2. Open the `avrig-watcher` client and rotate its secret. **Do not** change `confidential` or the enabled flows: the registration is correct for a backend service, and `client_credentials` is its only flow. While in there, the single unused `redirect_uris` entry `https://api.avrig.ai/auth/callback` can be removed in the same visit, because `client_credentials` has no redirect step.
3. Write the new secret to a `0600` file outside the repositories, or paste it directly into `D:\avrig\config\oidc.toml` as the `oidc.client_secret` value. Never put it in a shell argument, a log, or a chat transcript. Writing it into that one file is the preferred route, because it keeps the value out of the conversation and the agent then only has to copy one already-present value into the other two files.
4. `Infra` then patches `oidc.client_secret` in exactly three files, preserving owner, mode and every other byte: `/opt/avrig/config/oidc.toml`, `D:\avrig\config\oidc.toml`, `avrig-api/config/oidc.toml` (gitignored). Do **not** write the environment or the NSSM `AppEnvironmentExtra`; `oidc.client_secret` deserializes from TOML only, so an env edit fakes a rotation.
5. `Infra` restarts `avrig.service` and the Windows `avrig` service, then proves: new secret `200` with a token, old leaked value `401` (**not** `400`), all three files sharing one new hash prefix different from `6f8aadda98f7`, and the new token still reaching the knowledge endpoint.

Any one of these also clears G1:

1. **Rotate in the admin UI at `https://iam.avrig.ai/auth/v1/admin`** (the registered passkey satisfies MFA), write the new value to a `0600` file, and `Infra` does the three TOML patches, both restarts, and all proofs. No secret touches a log.
2. **Paste a live admin Bearer access token**, and `Infra` completes the `PUT` itself.
3. **Temporarily clear `force_mfa` on the `rauthy` client.** Not done unilaterally, because it weakens an admin control even if restored immediately.

Until one of these happens, G1 stays open and the leaked value keeps working. Do not tag 0.4.0 claiming G1 is satisfied.

**Consumers are safe.** `api_url` is commented out in all three watcher configs (`/opt/avrig/config/watcher.toml:5`, `D:\avrig\config\watcher.toml`, `avrig-api\config\watcher.toml:4`), so `main.rs` matches `(None, _, _) => None` and no token request is ever attempted. There is no Vault `client_secret_ciphertext` fallback either. Nothing can lose authentication when the secret rotates. One caveat: because the client is constructed from config at startup, re-enabling `api_url` later requires a restart to pick up a rotated secret. It is not hot-reloaded.

**The redirect URI stays.** `redirect_uris=https://api.avrig.ai/auth/callback` is inert under `client_credentials`, which has no redirect step, so Rauthy never validates it on a token grant. Removing it during a release-gated rotation is cosmetic risk for zero security benefit. Tidy it separately if at all.

### A streaming defect that works by accident

Both SSE clients dispatch on the event name, and neither names `answer_delta`, which is the name the server actually emits (five times in `main.rs`).

| Location | Handles | Misses |
| :--- | :--- | :--- |
| `apps/web/src/shared/api/client.ts:196` | `delta`, `answer`, `content` | `answer_delta` |
| `packages/api-client/src/index.ts:246` | `delta`, `answer`, `content` | `answer_delta` |

Streaming answers still render, but only because the server's payload is `{"delta": "..."}` (`main.rs:2519`, `SseAnswerDelta { delta: content }`), so the generic `else` branch at `client.ts:221-231` parses it and calls `onAnswerDelta`. Two consequences:

1. If the server ever renames the payload field, answers stop rendering with no error, because the event name was never matched.
2. The fallback also fires `onAnswerDelta?.(dataStr)` on any unparseable event, which would leak raw JSON into the answer bubble.

Not a release blocker: behaviour is correct today. Fix it in `0.5.0` by adding `answer_delta` to the name match in both clients and by making the generic branch stop guessing. It is recorded rather than done because changing SSE dispatch this late risks the streaming path that K10 verifies, and the current behaviour is verified working.
