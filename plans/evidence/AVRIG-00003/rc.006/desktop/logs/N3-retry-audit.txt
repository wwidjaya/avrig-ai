So the count has two shapes rather than one, and the audit separates them:

  RE-ISSUED AFTER AN ERROR, without a new snapshot: NONE.
  Used more than once for a deliberate read or for the row's own experiment: six refs, each
  accounted for above, and none of them a blind repeat of a failed command.

The ref lifecycle errors that actually fired on this run were INVALID_ARGS (E1, D6, D10 --app),
WINDOW_NOT_FOUND (three times) and AMBIGUOUS_TARGET (twice). Each was followed by a snapshot, a
listing, or nothing at all, never by the same argument again:

  after E1's INVALID_ARGS        -> a snapshot on the next line
  after E7's AMBIGUOUS_TARGET    -> pinned --window-id, the title never repeated
  after each WINDOW_NOT_FOUND    -> list-windows, or the end of the run

No STALE_REF was raised on this run, so there is no stale-ref retry to audit against; the closest
case is E2, where the tool did NOT raise STALE_REF and the row's own instruction is to record that
silence as the finding rather than to retry into it.

One judgement, repeated from E6 rather than buried: the two close-app TIMEOUTs were followed by
further work on the same application. That was not a retry of the same command. The pending save
prompt was read from a fresh snapshot and dismissed through its own Don't save ref first, and the
close was then completed through the window's own Close ref, which is a different command against
a different state.
