=> ## Desktop UAT Testing
=> 
=> A desktop responsibility that cannot be executed is a sentence, not a test. This section states exactly how to run the loop against a native window, and it sits beside the browser contract rather than inside it.
=> 
=> ### When it applies
=> 
=> - Mandatory whenever the plan changes or exercises `apps/desktop`, `avatar/pet-desktop`, or any native window a user operates directly. A Tauri window, a Bevy overlay, a tray menu, a native dialog, and an installer are all desktop surfaces.
=> - Not applicable only when the plan genuinely has no window, which means nothing is started, clicked, or read on screen. Record `not applicable` with a one line reason in the matrix and in the result line, and never leave the row silent.
=> - A surface that exists but could not be reached, such as a binary that will not start or a session that cannot render, is BLOCKED with the failing envelope attached. It is never not applicable, and it is never downgraded to a browser check.
=> - A plan that touches both a page and a window needs both harnesses. Playwright does not see a native window, and `agent-desktop` does not see page internals, so neither substitutes for the other.
=> 
=> ### Preflight
=> 
=> Run the preflight before the first action, and save every envelope it prints.
=> 
=> ```text
=> agent-desktop status            # platform, permission state, and supported surfaces, expect ok: true
=> agent-desktop version
=> agent-desktop list-surfaces
=> ```
=> 
=> - Record the platform, the permission state, and the supported surfaces that `status` reports. On Windows the permission state comes from `status`. Do not reach for `agent-desktop permissions --guide`, which walks the macOS Accessibility grant and is macOS only.
=> - Save the `agent-desktop version` output into the evidence folder, because the bundled guides are matched to that binary and a later reader needs to know which release produced the evidence.
=> - If `status` fails, the row is BLOCKED with the failing envelope attached. Do not continue in the hope that the first ref action works.
=> - Run `where.exe agent-desktop` once. If the command does not resolve, the row is BLOCKED and the recovery command is named.
=> 
=> ### Read the bundled guides before the first action
=> 
=> The binary ships its own guides, they are version matched to it, and they win over anything memorized, copied from a prompt, or quoted in an older plan.
=> 
=> ```text
=> agent-desktop skills get desktop     # the loop, the ref rules, the retry rule
=> agent-desktop skills get platform    # this platform's specifics, the Windows guide on this host
=> ```
=> 
=> Read both at the start of a session, before the first snapshot, and follow them. Save both to the evidence folder as `guide-desktop.txt` and `guide-platform.txt`. When a form in this section and a form in a guide disagree, the guide is right, and the difference is a defect in this definition worth reporting rather than a licence to improvise.
=> 
=> ### The observe, act, verify loop
=> 
=> The loop is snapshot, act on a ref from that snapshot, snapshot again, assert. There is no model inside the tool, so the observing and the asserting are yours.
=> 
=> ```text
=> agent-desktop snapshot --app "Notepad" -i
=> agent-desktop get '@s8f3k2p9:e8'
=> agent-desktop click '@s8f3k2p9:e8'
=> agent-desktop snapshot --app "Notepad" -i
=> ```
=> 
=> - A ref is qualified: `@<snapshot_id>:e<N>`, for example `@s8f3k2p9:e8`. Every example in this section uses that form, because it is the only accepted one.
=> - A ref belongs to exactly one snapshot. A snapshot id from an earlier run is not reusable, and a ref taken from `@s8f3k2p9` means nothing in a snapshot whose id is different.
=> - A bare `@e8` or `e8` is rejected with `INVALID_ARGS`, and the envelope names the expected shape. Do not try to repair a bare ref by guessing a snapshot id.
=> - Take a fresh snapshot after every action that can change the tree, and after any navigation, dialog, or menu. A ref from a stale snapshot points at a node that no longer exists.
=> - `delivered_verified` in an envelope is not evidence and never satisfies a check on its own. The following snapshot is the evidence, for every act and not only for a secret step, because the tool has been observed certifying an empty value as delivered.
=> - `STALE_REF` and `AMBIGUOUS_TARGET` both mean take a new snapshot. They never mean retry the same ref.
=> - Take the actions a node offers from the snapshot, because `get` does not report them. `agent-desktop is '<ref>'` answers a predicate question, and `agent-desktop find` locates a node when you have a name rather than a ref.
=> - `toggle`, `select`, and `scroll-to` are the other ref actions. `press` sends a key, `wait` waits for a condition or a settle, and `focus-window` brings a specific window forward.
=> - When the tree is dense, `agent-desktop snapshot --app "<app name>" --skeleton --compact` gives the shape without every child, then `--root '<ref>'` drills into the subtree you care about.
=> 
=> ### Windows and PowerShell specifics
=> 
=> - Quote every ref as a single quoted string: `agent-desktop click '@s8f3k2p9:e8'`. PowerShell treats a leading `@token` as the splatting operator, so an unquoted ref is parsed as a variable before the CLI ever sees it.
=> - `type`, `focus`, `right-click`, `double-click`, and `triple-click` need `--headed` on this platform, and they drive physical input. `type` synthesizes keystrokes through SendInput, so it is a permissioned exception rather than the default text path.
=> - `get '<ref>'` reads one named property, one of `text`, `value`, `title`, `bounds`, `role`, or `states`, and it never reports `available_actions`. Take the actions a node offers from the snapshot instead.
=> - The headless path for text is `set-value --stdin`, called through `agent-desktop.cmd` or the native executable rather than the `.ps1` shim, and piped so the value never enters the argument list:
=> 
=> ```powershell
=> 'uat-secret-0002' | agent-desktop.cmd set-value '@s8f3k2p9:e8' --stdin
=> ```
=> 
=> - A `POLICY_DENIED` from a headless command is a finding about the headless path. It is never a reason to rerun the same step with `--headed`, which is used only where the plan permitted physical input and the application demands real keystrokes.
=> - `snapshot --app` does not raise `AMBIGUOUS_TARGET` when an application has several windows. It silently takes the focused window and returns `ok: true`, so a run can read the wrong window while looking healthy. Whenever `list-windows --app "<app name>"` shows more than one window, pin the intended one with `--window-id <id>` rather than relying on focus.
=> - When a snapshot does return `AMBIGUOUS_TARGET` and lists candidate windows, pin one with `--window-id <id>` taken from that list rather than guessing which window was meant.
=> - `list-apps` and `list-windows` confirm what is on screen before acting. `list-windows --app "<app name>"` gives window ids usable as `--window-id`.
=> - A window with no interactive children is a finding about the application, not a tool failure. Record it with the snapshot attached. A transparent, always-on-top Bevy overlay is the usual case, because a GPU canvas exposes almost nothing to UI Automation.
=> 
=> ### Launch the tested artifact
=> 
=> - Launch the binary built from the candidate tag commit, never a local rebuild. Name the artifact path in the matrix, and resolve the commit with `git rev-parse <code-lower>/<NNNNN>/rc.<NNN>^{commit}` the same way the browser contract does.
=> - `agent-desktop launch` is the entry point when the application is not already running. `list-apps` and `list-windows` confirm what arrived on screen, and `focus-window` brings it forward.
=> - Close what you opened with `agent-desktop close-app`, then confirm with a follow up `list-apps` that it is gone. Never leave an application you launched running, and never leave a `--headed` run alive.
=> - A hosted application is the exception, and it must not be reported as a tool failure. `--app` resolves against `list-apps`, and a modern hosted application appears there under its host process, typically `ApplicationFrameHost.exe`, so `close-app "<App>.exe"` answers `APP_NOT_FOUND` demanding the exact process identity even while `list-windows --app "<App>.exe"` finds the window. Verified against `CalculatorApp.exe` on this host. For a hosted application, close through the window's own Close ref taken from a fresh snapshot, then confirm with `list-windows` that the window is gone, and record that route in the evidence.
=> - `agent-desktop batch '<json array>'` runs several commands in one call, and its JSON sits in the process arguments. It is fine for a read only sequence and never for a secret step.
=> 
=> ### Secrets
=> 
=> - Any token, password, or key reaches the application through `--stdin` or a separate `clipboard-set` step, never as a process argument. Arguments are visible to anything that can read the process table or a shell history, and they land in the transcript of the run.
=> - `--stdin` is still the rule for a secret, but call it through `agent-desktop.cmd` or the native executable, never through the `agent-desktop.ps1` shim. The shim is `& ...agent-desktop-win32-x64.exe @args`, and PowerShell does not forward a script's pipeline into a native command invoked inside it, so `--stdin` arrives as EOF, the tool writes an empty value, reads it back empty, and returns `ok: true` with `delivered_verified`: a credential sent that way is silently lost while every envelope looks healthy. Through the `.cmd` or the native executable the value does land, but the same act returns `ACTION_FAILED` with no `value` in `post_state`, which is a false negative rather than a failed delivery.
=> - Always confirm the value by reading it back with `agent-desktop get '<ref>'` and asserting it in the next snapshot. `type --stdin` also reads stdin, but on Windows it is keystroke synthesis that needs `--headed`, so it applies only where the application rejects a direct value and the user has permitted physical input.
=> - `clipboard-set --stdin` followed by a paste in the application is the second acceptable route, with `clipboard-clear` afterwards so the value does not sit on the clipboard.
=> - `batch` puts its JSON in the process arguments, so no secret ever goes in a batch.
=> - Evidence stays inside `plans/evidence/`. A snapshot, a screenshot, or a clipboard dump from a live desktop can carry private content, so it is never pasted into a public issue, a commit message, or a result line.
=> 
=> ### Retry discipline
=> 
=> - Retry only when `error.disposition.retry` is `safe` in the envelope. Read that field rather than deciding that a failure merely looks transient.
=> - Any other disposition is a finding, reported with the error code quoted. An `INVALID_ARGS`, a `STALE_REF`, or a `POLICY_DENIED` is never retried as it stands.
=> - A stale ref is followed by a new snapshot, not by a second attempt at the same ref. Retrying the same ref turns a loud failure into a quiet click on the wrong control.
=> - Do not wrap a desktop call in a sleep and a loop to paper over a race. Use `agent-desktop wait` for the condition, and keep `Start-Sleep` out of the recorded step.
=> 
=> ### What to assert
=> 
=> - Assert on the accessibility tree: the role and name of the node, and visible state transitions such as a value appearing, a control becoming enabled, or a dialog opening and then closing.
=> - The second snapshot is the assertion. A node that is gone, or a value that did not change, is the finding.
=> - `wait --text` cannot match a value held in a control, so a value is asserted with `get`, never with `wait`. Use `wait` for a condition that appears as text in the tree, and read a control's value back by name.
=> - Screenshots are supporting evidence and never the assertion, because a picture cannot tell a correct disabled state from a broken one.
=> - A notification check uses `agent-desktop list-notifications --headed`, or a run where the Action Center is already open. On Windows that command returns `POLICY_DENIED` headless while the center is closed, so it is conditional rather than a default assertion, and a `POLICY_DENIED` there is a preflight state rather than an application finding.
=> 
=> ### Evidence per run
=> 
=> Capture evidence under `plans/evidence/<CODE>-<NNNNN>/rc.<NNN>/desktop/`, keyed by the same candidate number as the browser evidence for the same run:
=> 
=> ```text
=> plans/evidence/<CODE>-<NNNNN>/rc.<NNN>/desktop/
=>   snapshots/          every snapshot envelope, exactly as printed
=>   screens/            one screenshot per asserted state
=>   version.json        agent-desktop version output
=>   status.json         agent-desktop status output
=>   guide-desktop.txt
=>   guide-platform.txt
=>   RESULT.md           one result line
=> ```
=> 
=> - Save the snapshot envelopes, one screenshot per asserted state, the `version` output, and the `status` output. A paraphrased envelope cannot be re-read when a result is questioned, so save what the tool printed.
=> - The result line names the candidate tag, the commit SHA, the installed CLI version, the verdict, the count of passing checks, and this folder path.
=> - The envelope carries a `version` field of its own, which is the schema version of the envelope and not the CLI version. Keep the two apart: the schema version describes the JSON shape, and the CLI version describes the binary that produced it. Neither of them is a product release version.
=> - The edit to this definition is untracked in the Agentic checkout, so no candidate tag can contain it. Its proof is the instruction manifest at `plans/evidence/<CODE>-<NNNNN>/instruction-manifest.json` together with a read-back of the hashes it records, while the candidate tag proves the rest of the tree.
=> - Follow the project's evidence retention policy rather than committing large binaries by default. A desktop claim with no envelope in that folder counts as not tested, and the verdict line must say so.
=> 
=> ### Reporting a desktop failure
=> 
=> Report the failing ref or window id, the expected role and name, the actual role and name, the snapshot path, the screenshot path, and the artifact path that was launched, plus the same structured diagnostics used elsewhere: scenario name, expected versus actual behaviour, root cause hypothesis (`be`, `fe`, `edm`, `Infra`, or `build`), reproduction steps, and the relevant envelope excerpt. An application that exposes no interactive children is reported as a finding about that application, with its snapshot attached, rather than as a broken harness.
