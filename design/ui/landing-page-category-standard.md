# Avrig Landing Page, Category Standard Direction

**Status:** User selected, code-first static prototype
**Audience:** Prospective evaluators and returning operators equally
**Craft references:** Linear and Vercel, as named by the user
**Artifact:** `landing-page-category-standard.html`
**Source of product truth:** Vault design definitions and repository `AGENTS.md`

## THESIS

Avrig is a virtual engineering company whose work moves through an ordered lifecycle under human authority. The page should explain the product quickly, show how its company model and engineering system fit together, and give returning users a direct path to the workspace.

## OWN-WORLD

The selected world is the category-standard product landing page, played straight. Use familiar product navigation, clear section hierarchy, concise explanatory copy, a real product model as the hero visual, and restrained shadcn-style controls. The visual language uses white and soft neutral surfaces, near-black text, a single blue action color, thin borders, moderate corner radii, and light structural elevation. IBM Plex Sans is self-hosted for the display and body voice. It does not add a metaphor, novelty texture, or decorative spectacle.

Linear and Vercel set the expected level of product-page clarity and finish. They are craft references, not templates to copy. Avrig's own system model and governance rules supply the page's content.

## STORY

- First-time visitors understand that Avrig coordinates a virtual engineering company and a canonical engineering lifecycle.
- Returning operators can open the workspace from the navigation or closing action.
- The page demonstrates the Founder authority boundary, the two operating engines, the shared harness, and the authoritative record layer.
- The full lifecycle, organization model, knowledge model, module registry, and target technology architecture remain discoverable below the hero.
- Every architecture visualization is labelled as a definition or target view, never as live telemetry.
- Every illustrative artifact state is labelled as an example. No customer, usage, health, employee-count, or runtime claims are introduced.

## FIRST VIEWPORT

A short navigation sits above an asymmetric two-column introduction. The left column says what Avrig is in plain language and offers “See how it works” and “Open workspace”. The right column shows a labelled system map: Founder authority above the Office Operating System and Agentic SDLC Engine, with shared harness capabilities and authoritative records beneath. The map is explicitly an architecture definition, not live telemetry.

## FORM

- Direction seed: `seed:51f7befcc65774a0`. The user selected the category standard card from this direction round.
- Use semantic HTML landmarks and a single, descriptive page heading.
- Use a compact in-page navigation that remains readable on narrow screens.
- Keep the primary action dark and high contrast; use the blue accent for links and restrained highlights.
- Build the system map, lifecycle, and module registry from selectable text and CSS layout, not a raster screenshot.
- The Founder-to-engine connection draws in once as a quiet explanation of the relationship. All content is visible by default, and reduced-motion preferences remove the animation.
- Keep each ordered stage in DOM order. Do not present lifecycle steps as a reorderable workflow.
- Provide visible keyboard focus, a skip link, reduced-motion support, and responsive layouts without horizontal page overflow.
- Use no fabricated runtime status or implied live approval.

## Product definitions included

The page includes the central definitions from the vault's System Architecture, Technology Architecture, and Knowledge Management documents: Founder, CEO/PET, Personal Assistant, persistent employee identity and ephemeral runtime, departments and project teams, Office OS and SDLC Engine, shared harness and record layers, the 16 canonical stages and optional deployment, human-only approval, artifact lifecycle, version-pinned traceability, all six epistemic statuses, project-knowledge precedence, the knowledge lifecycle, module codes, and the target technology stack. The target technology view is labelled as a design definition, not implementation status.

## Explicit exclusions

No testimonials, benchmark numbers, customer names, operational counts, online indicators, invented artifact hashes, invented live approvals, or assertions that every target module is implemented.
